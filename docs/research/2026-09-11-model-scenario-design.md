## Confirmed boundary

- Persist immutable engine snapshots and exact source versions; database UUIDs, graph identity and revision history do not replace engine IDs or hashes.
- Store exact engine canonical snapshot bytes plus schema/hash, calculation version, cutoff and immutable corpus/input pins. JSONB may hold query projections, but must not become the authority for reconstructing canonical bytes.
- Bull/base/bear are sparse immutable scenario revisions over a shared base graph. Reported facts remain unchanged. The base scenario has no overrides and directly references its base snapshot: the engine's `Scenario` constructor rejects empty overrides.
- Graph, version, scenario, source and active-pointer references enforce organization and relevant workspace/graph/version scope. Enable and force RLS, grant only required API/worker operations, and enforce immutable history in PostgreSQL as well as application code.
- #64 owns graph/scenario persistence and API integration; #65 owns model UI, #66 owns forecasting, and #68 owns export artifacts. This slice adds no forecasting methods, charts, export system or automatic financial assumptions.

## Decisions that must be resolved before contract freeze

1. **Eligible source facts.** An approved payload is not necessarily an engine `SourceFactNode`. That node contains one Decimal and hard-codes `REPORTED` provenance. Approved payloads also include derived KPIs, management assertions, ranges, floors/ceilings, qualitative guidance and revenue-driver descriptions. Recommend the first slice admit only approved, reported scalar facts with unambiguous mappings. Do not select a range midpoint, infer a missing bound/value, or relabel management guidance as reported. Confirm whether this narrow initial eligibility satisfies #64; broader guidance or derived-fact support needs an explicit provenance/node contract decision, not a convenience adapter.
2. **Unit, period and value mapping.** Extraction units are strings; engine units are closed currency/count/percent/ratio types and periods are fiscal quarter/year. Freeze an explicit supported mapping and reject ambiguity, missing currency/calendar, unsupported instant/trailing/forecast periods and incompatible dimensions. Normalized extraction `value` retains its `scale`: `"100"` with scale `6` means 100 million. Conversion must apply the scale exactly once, preserve sign, use exact Decimal arithmetic and satisfy engine precision/exponent bounds. Percent 60 remains 60%, not ratio 0.6 without an explicit conversion. Keep the immutable original payload/pins; never rewrite approved values to make them fit.
3. **Evidence and historical availability.** `SourceFactNode` has one `source_span_id` and an optional `fact_id`; approvals may contain multiple evidence spans. Decide whether eligibility requires one designated supporting span or whether a reviewed deterministic primary-span rule is acceptable. All supporting evidence and the exact approval version still belong in the database source binding. Also specify historical eligibility for a newly approved/corrected version citing an older document: document publication time and approval creation time are different facts. Do not silently substitute one for the other or invent a #66 vintage policy. A source must satisfy the frozen model/source cutoff and #61's complete evidence checks; legacy NULL validation context is unknown and needs an explicit eligibility rule.
4. **Scenario revision semantics.** Recommend each bull/bear revision supply its complete sparse override set against the same pinned base, with a fresh engine scenario ID. Keep stable scenario identity/label separate from revision ID and engine ID. Revision ancestry can point to the prior scenario revision while each resulting snapshot branches from the base. Confirm this replacement-layer model rather than stacking changes on a previous derived snapshot: both can be expressed with the engine, but they produce different lineage. Reusing an engine scenario ID on an already-applied layer can collide with generated node IDs. Setting a workspace's active scenario should remain an explicit optimistic-concurrency action; do not silently activate newly created revisions.

These are product/domain choices, not reasons to change canonical encoding, calculation formulas or financial validation. Unsupported cases should fail with a typed explanation before any write. A new approval head or changed workspace cutoff must not retarget or invalidate the reproducibility of an existing stored model version.

## Minimal persistence contract

Use the six entities already assigned by canonical plan section 7, with no duplicate ledger:

| Entity | Required boundary |
| --- | --- |
| `model_graphs` | Stable scoped identity; current-version pointer constrained to this graph/workspace/organization. |
| `model_graph_versions` | Immutable engine snapshot, parent reference, exact canonical bytes/hash/schema and frozen calculation/source/corpus/cutoff pins. Parent must belong to this graph. Do not make `(graph_id, version_number)` unique: engine version is ancestry depth and valid branches share it. |
| `model_nodes` | Version-scoped typed projection. Source nodes bind the exact immutable approved record/version, never its mutable latest head. Keep source binding outside the unchanged engine encoding unless the reviewed contract explicitly requires a new schema. |
| `model_edges` | Same-version endpoints, role and deterministic order, derived from the constructed engine graph. Include `iteration_seed` edges generated from iteration groups, not only `Node.inputs()` edges. |
| `scenarios` | Immutable revisions with stable scenario identity, label, pinned base version, parent revision, engine scenario ID where applicable, as-of and resulting snapshot reference. Constrain all references to the same graph/workspace/organization. |
| `scenario_overrides` | Sparse unique target/value rows scoped to a revision and its base version; targets must be existing eligible assumptions/drivers. Engine validation remains authoritative for node-kind eligibility, finite Decimal values and derivation. |

Insert canonical version, nodes, edges, source bindings, scenario/override rows where applicable, head update, audit and request receipt atomically. Do not persist a partially projected or unverified graph. A schema check cannot prove arbitrary JSON payloads equal an engine snapshot; the API must verify this before insertion and the loader must reject corruption rather than repair it silently. Database guards prevent later UPDATE/DELETE of immutable data and restrictive foreign keys prevent source/history deletion.

Add the active pointer FK `(workspaces.active_scenario_id, workspaces.id, workspaces.org_id)` to `(scenarios.scenario_id, scenarios.workspace_id, scenarios.org_id)` as the canonical plan requires. The migration must explicitly preflight every non-null reserved pointer and abort on invalid references; it must not clear pointers, fabricate scenarios or infer their workspace. Update the pointer comment in the new migration; leave migration 0009 unchanged. The integration lead must allocate the next migration number after the #278 queue is settled.

Restore means a new child of the current graph version containing the selected historical content and a `restored_from` audit reference. It must not rewind the current pointer to an old immutable version or discard iteration groups, source pins or scenario lineage. Source eligibility/cutoff checks for a newly created child cannot silently widen time or silently drop historical inputs; the contract must distinguish reproducing an old artifact from creating a new child under current workspace constraints.

## Smallest API/engine slice

The engine currently has canonical serialization but no persisted-snapshot decoder. Add a closed typed decoder beside `snapshot.py`: reconstruct supported v1/v2 node, unit, period, formula and iteration-group types, verify the supplied snapshot hash, and require exact canonical re-encoding. Reject duplicate JSON keys, unknown schemas/types/fields, floats, malformed tags and resource overflow. Rebuilding every decoded version as a new root would reset parent/version/scenario metadata and is incorrect. Do not add arbitrary class loading, pickle, eval, or change the existing canonical serializer/hash algorithm.

Keep PostgreSQL and tenancy in an API-side store/adapter; the engine remains database-independent. Follow the existing `SnapshotStore` semantics of hash verification, idempotent identical insertion and parent-before-child lineage, adding tenant-scoped database identities and transactional projections. Do not rely on a globally unscoped snapshot hash lookup to authorize reads.

Freeze only the commands and reads needed to establish these behaviors:

- Create a graph and its initial version from explicitly selected approved versions and an explicitly specified graph; append a version against an expected head; retrieve an exact version and bounded version history. Do not invent automatic graph construction from all approved facts in a workspace.
- Create/read a base scenario; create bull/bear revisions with the approved sparse-layer semantics; read exact revisions and bounded history; restore a selected version as a new child.
- Continue using the existing workspace PATCH to select `active_scenario_id`, with actual same-workspace authorization and a typed failure before a PostgreSQL constraint error can become an HTTP 500. Preserve existing workspace ETag handling.

Use exact immutable IDs on commands and responses. Reuse tenant membership, safe error envelope, request receipts and scoped keyset pagination conventions. Freeze role permissions using existing owner/editor/reviewer/viewer semantics; recommend owner/editor mutations and all-role reads, subject to product confirmation. Use opaque ETags for mutable graph/workspace heads, stable idempotency keys for exact retries, 412 for stale expectations, 409 for changed-body key reuse and 413 for explicitly bounded resources. A failed command writes no version, head change or receipt claiming success. Match existing receipt-first replay behavior so an exact retry succeeds after the head has subsequently changed.

Node/edge counts, canonical bytes, total source bindings and decode/derivation work need explicit measured limits before freeze. Bound work before expensive parsing/projection, and return complete results or typed failure. Existing engine performance fixtures can inform limits; neither an arbitrary 500-line module target nor a UI page size is a graph complexity budget.
